一、调度器版本、用途摘要
================================================================================

1. scx_cake  (scheds/rust/scx_cake, 版本 1.1.2)
   - 面向 AMD/Intel 现代游戏平台的 CPU 调度器，思想借鉴网络 CAKE (DRR++)
   - 4 类任务：GAME / NORMAL / HOG / BG，自动识别 Steam/Wine/Proton 进程
   - Per-LLC DSQ 分片、EEVDF 风格加权、无全局原子操作
   - README 明确要求 Linux 6.12+

2. scx_lavd  (scheds/rust/scx_lavd, 版本 1.1.1)
   - Latency-criticality Aware Virtual Deadline 调度器
   - 主要为交互 / 游戏工作负载设计，兼顾吞吐与尾延时
   - 依赖 futex 追踪（ftrace 或 tracepoint）提供 lock holder 时间片扩展
   - CI 里将 stable/6_12 列入 blocklist（issue #3046），暗示实际最小可用
     内核版本 > 6.12

3. scx_layered  (scheds/rust/scx_layered, 版本 1.1.1)
   - 多层可配置的 BPF/用户态混合调度器（Meta 出品）
   - 按 cgroup / 匹配规则将任务分层，每层独立策略
   - 支持 GPU 感知、antistall、util-compensation、queued wakeup 等

二、每个调度器最低可运行的内核版本
================================================================================

【结论】

  调度器          官方 README 门槛   实际最低（含硬依赖）   备注
  ---------------------------------------------------------------------------
  scx_cake        v6.12+             v6.12 + BPF Arena       硬编译期依赖 BPF
                                     （即 ≥ v6.12 sched_ext  Arena（v6.10 引入）
                                       + ≥ v6.10 BPF Arena）
  scx_lavd        v6.12+             同上                    同上；且 CI 已排除
                                                             stable/6.12
  scx_layered     v6.12+             v6.12 sched_ext         不硬依赖 BPF Arena
                                     （建议 ≥ v6.15/6.16）    （build.rs 未链接
                                                             lib/arena.bpf.c）

【依据】

- scx 上游 README.md 第 34 行：
    “sched_ext is supported by the upstream kernel starting from version 6.12”

- scx_cake/README.md 明确写：Kernel = Linux 6.12+

- 三者 build.rs 差异（关键）：
    scx_cake/build.rs   显式添加 lib/arena.bpf.c、lib/sdt_alloc.bpf.c，
                        cake.bpf.c 亦 #include <lib/arena_map.h>
    scx_lavd/build.rs   显式添加 lib/arena.bpf.c、lib/sdt_alloc.bpf.c，
                        使用 ArenaLib::init() 加载
    scx_layered/build.rs 只链接 timer/util/pmu，没有 arena.bpf.c，
                        主 BPF 代码不引用 arena_map.h / __arena，
                        任务上下文用 BPF_MAP_TYPE_TASK_STORAGE 完成

- 三者共享的 lib/ 头文件包含 scx_bpf_now、scx_bpf_select_cpu_and、
  scx_bpf_cpu_curr、scx_bpf_dsq_peek、bpf_cpumask_populate 等 kfunc。
  上游 scheds/include/scx/compat.bpf.h 已给出 __COMPAT_ 宏，对多数运行时
  kfunc 缺失做了回退；因此 v6.12 sched_ext 基线即可加载调度器骨架，但
  编译期 BPF Arena 属性（addr_space_cast、__arena 指针、BPF_MAP_TYPE_ARENA
  map 类型）是一个**加载期硬门槛**。

【尚未回合，可能影响运行的特性】

  经 grep 全内核 C 源文件确认，下述 kfunc/接口在当前分支未出现：

    1. BPF Arena 全系（*硬缺失*，影响加载）：
         · kernel/bpf/arena.c 源文件缺失（Makefile 未编入，只有旧的
           arena.o 遗留）
         · 无 addr_space_cast 指令、无 PROBE_MEM32 JIT 支持
         · 无 bpf_arena_alloc_pages / bpf_arena_free_pages
         · 无 __arg_arena、btf_decl_tag("arg: Arena")
         · 无 BPF_MAP_TYPE_ARENA / BPF_F_MMAPABLE 配套 arena 处理

       备注：paul/scx-scheduler-set2 分支上已经引入过上述 BPF Arena
       系列补丁（dc5fb07a9a63 “bpf: Introduce bpf_arena.” 等约 40
       个提交），但在 set3 上尚未合并/带过来。

    2. bpf_cpumask_populate（v6.15）
         · scx_bitmap_to_bpf 会退回到 __COMPAT_ 分支并返回
           -EOPNOTSUPP。lavd/cake 中若 scx_bitmap_to_bpf 被实际调用
           将 bpf_printk 报错。

    3. scx_bpf_cpu_curr（v6.18）
         · lavd/layered 通过 __COMPAT_scx_bpf_cpu_curr 走 fallback，
           读 scx_bpf_cpu_rq(cpu)->curr。因为 scx_bpf_cpu_rq 已存在，
           **fallback 可用**，不阻塞。

    4. scx_bpf_dsq_peek（v6.19）
         · lavd 通过 __COMPAT_scx_bpf_dsq_peek 使用
           bpf_iter_scx_dsq_new + _next + _destroy 回退，**可用**，
           仅性能略差。

    5. scx_bpf_dsq_reenq（v6.20）
         · 三者未使用，不影响。

    6. scx_bpf_task_set_slice / _set_dsq_vtime（v6.19）
         · 三者未使用，不影响。

    7. ops.cgroup_set_idle（v6.19）、ops.sub_attach/detach/
       sub_cgroup_id（v7.1）
         · 三者未使用，不影响。scx_utils::compat.h 的 SCX_OPS_OPEN
           在字段缺失时会 WARN 并 NULL 掉，属于软兼容。

    8. SCX_OPS_ALWAYS_ENQ_IMMED（v6.19）
         · 三者未使用。

五、可否在 tkernel5 (set3) 上运行 —— 结论
================================================================================

  scx_layered
     可以运行（预期）。所需 kfunc、struct_ops 字段以及 SCX_OPS_ 标志
     tkernel5 均已具备；不依赖 BPF Arena；scx_bpf_cpu_curr 的缺失通过
     scx_bpf_cpu_rq 的 fallback 可正常工作；lo_fb / antistall / queued
     wakeup 等功能开关本身可关闭。首次上线需 `-t` 关闭 topology 时可
     绕过一些 NUMA 特殊路径便于验证。

  scx_cake
     **不能加载**。cake.bpf.c 直接 #include <lib/arena_map.h> 声明
     BPF_MAP_TYPE_ARENA map，且 build.rs 显式链接 lib/arena.bpf.c 与
     lib/sdt_alloc.bpf.c，编译期即依赖 BPF Arena。内核 verifier 将拒绝
     未知 map 类型。

  scx_lavd
     **不能加载**。同 scx_cake，build.rs 链接 arena.bpf.c 与
     sdt_alloc.bpf.c；main.rs 中 `ArenaLib::init()` 亦直接调用 arena
     初始化程序。此外 CI 已把 stable/6.12 拉黑（issue #3046），实际
     稳定运行建议 ≥ v6.14/6.15。

## 结论先行

要让 set3 支持跑 `scx_cake` / `scx_lavd`(arena)+ 全部三个(may_goto),从 `upstream` 需要且仅需要 **16 个内核提交**。已逐个验证:**都在 `upstream/master` 上、set3 都还没有**。

关键澄清两点:
- **用户态 libbpf/bpftool 不用动内核树**。scx 用自己 vendored 的 `local_crates/libbpf-sys`(2026 年的版本,早就懂 arena),内核树里的 `tools/lib/bpf`、`bpftool` 只服务于内核自带 selftests/samples,和你构建 scx 无关。所以之前清单里的 Group C(5 个 libbpf/bpftool 提交)**整组砍掉**。
- 之前担心的 **exceptions/bpf_throw 系列,确认不 pick**。arena 语义上不用它,它当年只是文本消冲突层。代价见下面"冲突面预警"。

**3. 遇到冲突时,先分类再动手(这是"干净"的核心纪律)**
- 冲突在 `arena.c`(新文件)→ 不可能冲突,忽略。
- 冲突在 `verifier.c` / `bpf_jit_comp.c` / `filter.h` / `core.c` → 几乎都是**上下文错位**(因为我们故意跳过了 6.7–6.8 的中间态改动),不是功能缺失。手动把新增 hunk 放到正确位置即可,**不要**因此去 pick 别的提交。
- 真判不准是不是缺前置:`git log upstream/master -- <冲突文件>` 看该文件在这两个补丁之间还有没有别的改动被你跳过;若那改动与 arena/may_goto 无关(比如 exceptions),就手工消冲突,不 pick。

**4. 每 pick 完一组就编译一次,尽早暴露问题**
```bash
make olddefconfig && make -j"$(nproc)" kernel/bpf/ arch/x86/net/
```
（组1、2 后编 `kernel/bpf/`;组5 后编 `arch/x86/net/`。分段编比全量快,也能把错误定位到刚 pick 的那组。）

**5. 功能验证(最终判据不是"编过",是"能 load")**
- 确认 uapi:`grep BPF_MAP_TYPE_ARENA include/uapi/linux/bpf.h`
- 起内核,`cargo build --release -p scx_cake` 后 `sudo ./target/release/scx_cake`,看 struct_ops 能否 attach、arena map 能否创建。
- 跑 `scx_layered` 验证 may_goto 路径。

## 冲突面预警(你选了最精简路线,要有心理预期)

因为**故意不带** 6.7–6.8 的 exceptions 及其它 BPF 中间提交,以下两个文件最可能报文本冲突,需要手工消:
- `kernel/bpf/verifier.c` —— may_goto(`011832b97b31`)和 arena verifier(`6082b6c328b5`)的 hunk 上下文假设了 6.9 期的 verifier,set3 是 6.6 期。
